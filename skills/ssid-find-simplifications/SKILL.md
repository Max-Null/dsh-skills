# 简化审查

把"找找能简化什么"变成**有证据的提案**。

**这是指导，不是清单：跟随代码，保持判断力；宁可少而扎实，也不要一堆薄猜测。**

**REQUIRED：** 涉及生命周期与拆除时用 `ssid-test-reliability`；涉及行文时用 `ssid-prose-standard`。同批安装。

## 从仓库上下文开始

- 读根 `AGENTS.md` 与 `seek-soul-in-darkness/AGENTS.md`，加 `docs/SSiD开发手册.md` §9（测试规范）。
- 判断任何壳或内核相关的东西之前，先读 `docs/设计/SSiD-壳级能力设计.md`——**与能力划分或事件分类对着干的简化需要额外证据**。
- **先搜 `docs/决策/` 里是否已有相关决策**（99 个文件，用关键词搜），再判断某处是否"没人要"。
- **默认认为下面这些是有意为之的，不要当作"低成本"删除目标**：`dsh-memory` 的 storage backend 抽象；壳/内核边界（`shell/main.mjs` ↔ `kernel.bundle.mjs` ↔ profile）。**动它们必须给出比现状更强的证据**，除非用户显式推翻。删除受保护接缝内一个未使用的方法或钩子仍然可以成立——只要不瓦解被保护的设计。

## 什么算强候选

**强候选**移除、折叠或降级某个真实存在的东西，并有明确证据表明当前设计**代价高于收益**：

- 一个公开方法、事件、配置项、注册表通知、helper、包、持久事件或测试产物**没有生产消费者**。
- 只有测试或文档在用它，而它们钉住的行为**不承重**。
- 两份表示**镜像同一事实**。
- 一个接缝上每个实现都必须支持、但**没有消费者使用**的方法。
- 一个包只为测试/演示/支持代码存在，并带来发布或依赖开销。
- 一个特性实现了**猜测性的产品通用能力**，没有产品属主。（**本仓库的实例清单留白**——不凭空编造，由实际使用填充；留白是有意的。）
- 一条回滚路径、一组期望输出或一个特例测试**只为保护一个未使用的 API** 而存在。
- 手搓代码重新实现了**维护良好的外部包或 Node 内置**已经提供的东西，换成它同时删掉实现与其专用测试。
- **简化后行为可以略有不同，但新行为仍然合理且更容易解释。**

**薄候选不够**：删一个错别字、跑一次未用代码扫描、移除一个有意记录的适配器，或者没有调用点证据的"这里看起来复杂"。

## 广泛普查

广度有帮助时用并行 subagent；给每个 agent 一个**域**，并要求**测量与生产调用点，而不是猜测**。**不要让第一个好候选中止普查。**

| # | 域 |
|---:|---|
| 1 | **壳与内核边界**：`shell/main.mjs` / `kernel.ts` / `kernel.bundle.mjs` / profile 装载 / splash 与部署流程 |
| 2 | **插件面**：13 个插件的注册点（storage backend / webServer / tools / slots / sessionProjections）、`cordis.patch.yml`、`dsh.client` 导出面 |
| 3 | **数据传输与状态**：session projection、storage backend、settings、MCP 注册项 |
| 4 | **测试与派生物**：`test/` 与 `tests/` 并存、Playwright 截图基线、`lib/` 与 `src/` 同步、vendor 三处副本 |
| 5 | **文档与规范**：手册、`docs/决策/`、插件 README 里的重复内容 |

**从最大的生产代码差异开始**——大范围审查若止步于显而易见的未用符号，会漏掉那些生命周期或防御机制承载主要成本的文件。

**vendor 与 profile-template 的副本是一类特殊候选**：它们是**同步链的产物**（手册 §10：四份指纹一致、改后必同步运行时实体）。删任何一处都会断链——**要么整体处理，要么不动**。

## 连同代码一起简化行文

**注释与文档是按面积维护的一部分**，用 `ssid-prose-standard` 判断。

- 删掉复述代码、或解释别处已经拥有的行为的注释；**保留必需的局部契约**。
- 文档留在它的属主层级；略去实现细节与罕见情形，除非它们改变被维护的契约。

## 审计信任与生命周期边界

对每个防御性拷贝、冻结、验证器与回调捕获，**点名值从哪里来、下一个所有者是谁**。同进程的类型化 service/plugin 调用**通常借用只读值**；解析器、配置装载、队列、模型/工具 JSON、持久文件、worker、进程与 wire 解码器**拥有或验证**它们的数据。

**围绕敌意 getter、伪造的类型化对象、回调替换、或同进程交接后突变构造的测试，是可能存在投机契约的证据，而不是保留它的自动理由。**

**本仓库的实际边界**：Electron 主进程 ↔ 渲染进程、内核 ↔ 插件、MCP 传输、`webServer` 路由。复杂异步代码要画出所有权图，把每个 sentinel、就绪 promise、取消路径、disposer 与状态标志映射到**独立的属主或转移点**；多个机制镜像同一条存活或结算事实时，提出**一个事务或生命周期控制器**。保留那些保护同步发布与回滚、回调约束、首个终止结果仲裁、worker/进程所有权或静默拆除的独立机制。

## 手搓代码与依赖

引入依赖是**正当的简化动作，不是政策例外**。对手搓的协议解析器、framer、重试/退避循环、glob 匹配器、diff 引擎一类基础设施，问：**维护良好的 npm 包或 Node 内置是不是已经做了这件事？**

像证明其他候选一样证明它，另加四条：

1. 读手搓实现，**点名该包覆盖的确切表面**；包里没覆盖的残余语义**算作反对交换的依据**，并留在提案里。
2. **诚实检查该包的健康度**（维护、采用、传递依赖足迹）；引擎底线已有内置时优先内置。
3. **先查 `docs/决策/`**：已被记录结论钉住的接缝，交换它必须**胜过那份记录的理由**，而不只是引用政策。
4. **算净删除量**：实现 + 专用测试 + 文档，**减去残留的胶水**。**只是把同样的复杂度搬个家的包装不算赢。**

**本仓库尚无成文的依赖政策**——引入依赖前先在提案里陈述上位理由。

## 证明或否证每个候选

动笔前先分类消费者：

| 语料 | 本仓库的范围 |
|---|---|
| **生产** | `max-null-plugins/*/src`、`seek-soul-in-darkness/plugins/*/src`、`shell/main.mjs`、`shell/kernel.ts`、`shell/scripts/`、`shell/profile-template/` |
| **非生产** | `test/` 与 `tests/`（**两者都要匹配**）、`lib/`（派生）、README、`docs/`、Playwright `baselines/` |
| **模糊** | `references/`（参考副本）、`.dsh-tmp/`、vendor 副本 |

先用 `rg` 找。好的搜索包括：确切符号、事件名、包名、配置键、带 `.name(` 与 `name(` 两种形态的方法名，以及 wire 字符串。然后读调用点、公开接口、动态事件名、测试、文档与装载路径。

**拒绝或降级一个候选，当**：

- 存在生产调用方，简化会变成**特性决策而不是清理**。
- 该 API 有已记录的决策或来之不易的防御模式作理由，而新证据**没有胜过**那个理由。
- 移除会引发无关改动，却**没有真正减少公开 API 或必需行为**。
- **想法正确但太小**——加一个有稳定标签的内联 TODO，而不是硬做成提案。

## 合并被取代的决策记录

**当一条新记录取代了旧记录时，在旧记录顶部加一行"已被 `<新文件名>` 取代"，并在新记录里链接旧记录。不删除**——`docs/决策/` 是历史。

**不要把每次简化普查都扩大成全仓库的记录审计。**

一条通用判断：**"先移除后加回"的功能是典型的取代案例**——但只有当该功能确已从生产代码、配置、schema、持久或 wire 格式、迁移与兼容行为中消失时，移除记录才可以独占其历史。

## 写决策记录

落点是 `docs/决策/YYYY-MM-DD-<标题>.md`。**本仓库目前没有简化类记录，所以第一条会是先例——按下面的结构写全。**

1. **`# <动作导向的标题>`**
2. **`## 问题`**：点名当前 API、引用相关文件、陈述消费者证据；**把生产调用方与测试/文档分开**。
3. **`## 提案`**：确切说明要**移除、折叠、降级还是换位**；相关时含测试、文档、README、JSDoc、基线截图与生成文件的清理。
4. **`## 为什么不保留它？`** 或 **`## 我们放弃了什么`**：**让最强的反方论证可被看见**。
5. **`## 验收标准`**：可观察的终态与门禁。
6. **`## 风险`**：公开 API 变更、行为变更、未来产品需求，以及为何这笔权衡仍然合理。

具体到"一个实施者能顺着痕迹走下去"。**避免"简化这个包"这类含糊提案**；与既有记录重叠时，**把有用的细节并入既有记录**而不是新建重复。

## 内联 TODO

内联 `TODO`/`FIXME`/`XXX` **只用于小而局部、明显有用但不是持久设计决策**的清理：

- **用稳定标签点名异味**，如 `TODO(double-default)`、`XXX(unused-default)`。
- **说明为什么可以安全重访、什么动作会简化它。**
- **不为投机性抱怨、或需要记录级决策的行为加 TODO。**

**本仓库目前零内联 TODO 标记**，待办集中在手册的「待办清单」节。采用前**先定紧迫度语义**（哪种标记代表什么紧迫度）——否则上一条的"想法对但太小"就**没有出口**，会变成"想法对但太小 → 忘掉它"。

## 折叠另一个分支

向 DSH 或第三方插件提 PR 前：diff 对照 `origin/master` 而不是当前分支，才能看到它的独立贡献。

- 移植达标的记录或 TODO；
- 把重叠材料**并入拥有该主题的既有记录**；
- **不为凑数移植重复或低置信度的提案**；
- 更新 PR 描述，让评审者看到真实的候选计数与范围。

## 验证与提交卫生

改动文档后**重跑受影响的 L1（typecheck + test）**；`git diff --check` 可以手动跑，但**本仓库没有钩子替你跑它**。

提交时要说明：

- 新增、合并、保留为部分取代、删除了多少条记录与内联标记；
- 主要普查了哪些域；
- **有意排除了什么**；
- 跑过了哪些检查。

**报告一个没有合格候选的结论同样有效**——说出你保留了哪些代表性的部分情形。
